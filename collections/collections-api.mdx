Collections are the primary method to credit a PeoplesPay account. Money may be collected via mobile money or bank card.

## Authentication
The first step in a PeoplesPay collection is token generation. By calling the [/hub/token/get](/api-reference/endpoint/get-token) endpoint
with the correct payload, the platform issues a time-limited access token that authorizes subsequent collections requests. This JWT access token
encodes the merchant's `appId` and the type of operation.

## Payment methods
<Info>
The request payload varies based on the collection's method of payment.
    
</Info>
<AccordionGroup>
<Accordion
title="Mobile money"
>
 Mobile money collections have peculiar considerations. The exact flow looks something like this:
 <Steps>
    <Step title="Initialisation">
        The collection is initialised as the POST request is sent to the momo collections [endpoint](/api-reference/endpoint/collect-momo).
    </Step>
    <Step title="Capture">
        The PeoplesPay platform communicates with the corresponding network provider's servers to trigger an payment prompt on the payer's phone
    </Step>
    <Step title="Approval">
        The payer approves (or declines) the payment
    </Step>
    <Step title="Notification">
        The network provider's systems notify the PeoplesPay platform of the collection outcome
    </Step>
 </Steps>
</Accordion>
<Accordion
title="Card"
>
 Collections performed by bank card are quite different to mobile money collections. The flow is as follows:
 <Steps>
    <Step title="Initialisation">
        The collection is initialised as the POST request is sent to the card collections [endpoint](/api-reference/endpoint/collect-card).
    </Step>
    <Step title="Card scheme gateway">
        The PeoplesPay platform communicates with a card scheme gateway to proceed
    </Step>
    <Step title="Approval">
        The payer approves (or declines) the payment
    </Step>
    <Step title="Notification">
        The network provider's systems notify the PeoplesPay platform of the collection outcome
    </Step>
 </Steps>
</Accordion>
</AccordionGroup>


## Event notification
Collections are asynchronous requests, so the immediate HTTP response indicates whether the collection request has been _received_ and initiated, not it's completion.

Upon transaction status update, a notification will be delivered to the supplied webhook endpoint, which is the URL passed in the `callbackUrl` field. The HTTP notification will have the following structure:
```json
{
  "eventId": "68a35303b0bab4e3f5fd3000",
  "transactionId": "68a34f028f75ffbd7f3bbc00",
  "amount": 0.1,
  "status": "paid",
  "date": "2025-01-01T00:06:00.500Z",
  "message": "SUCCESSFUL",
  "success": true,
  "code": "00",
  "externalTransactionId": "running-a-test-on-1755533058"
}
```
<Warning>
    Without providing a `callbackUrl`, you will not receive webhook notifcations. Ensure your request payload includes that field.
</Warning>


The supplied `callbackUrl` must return an HTTP `200` response upon receiving the notification above, so the PeoplesPay platform can consider the event notifcation as delivered. The `eventId` can be [retrieved manually](/api-reference/endpoint/get-event), or even triggered again at a later date. Additionally, the transaction can be looked up manually using the `transactionId` field value.
<Note>
    Find out more about events on the [dedicated page](/events/event-webhooks).
</Note>
