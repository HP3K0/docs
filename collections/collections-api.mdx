<Badge color="purple">Asynchronous flow</Badge>

Collections are the primary method to credit a PeoplesPay account. Money may be collected via mobile money or bank card.

## Authentication
The first step in a PeoplesPay collection is token generation. By calling <Badge color="blue">POST</Badge> [/hub/token/get](/api-reference/endpoint/get-token-collection) with the correct payload, the platform issues a time-limited access token that authorizes subsequent collection requests. 
<Check name="Best practice">
It is a good idea to cache this token. It's time-to-live is 60 minutes.
</Check>

The request payload varies based on the collection's method of payment.

<Accordion

 Mobile money collection flow looks like this:
 <Steps>
    <Step title="Initialisation">
        The collection is initialised as the <Badge color="blue">POST</Badge> request is sent to the momo collections [endpoint](/api-reference/endpoint/collect-momo).
    </Step>
    <Step title="Capture">
        The PeoplesPay platform communicates with the corresponding network provider's servers to trigger an payment prompt on the payer's phone
    </Step>
    <Step title="Approval">
        The payer approves (or declines) the payment
    </Step>
    <Step title="Notification">
        The network provider's systems notify the PeoplesPay platform of the collection outcome
    </Step>
 </Steps>
</Accordion>

 Collections performed using a bank card are a little different to mobile money collections. The flow is as follows:

    </Step>
    <Step title="Approval">

    </Step>

        The network provider's systems notify the PeoplesPay platform of the collection outcome

 </Steps>

## Post-initiation
Collections are **asynchronous** requests, so the immediate HTTP response indicates whether the collection request has been _received_ and initiated, not its completion.

Once PeoplesPay receives details on the collection from the processing entity, it will update the transaction status, which creates an event and fires a webhook notification. This notification is delivered to the supplied webhook endpoint, which is the URL passed in the `callbackUrl` field. See the shape of the [event object here](/api-reference/events).
<Warning>
    Without providing a `callbackUrl`, you will not receive webhook notifications. Ensure your request payload includes that field.
</Warning>


The supplied `callbackUrl` must return an HTTP `200` response upon receiving the webhook notification, so the PeoplesPay platform can consider the event notification as delivered. The `eventId` can be [retrieved manually](/api-reference/endpoint/get-event), or even triggered again at a later date. Additionally, the transaction can be [looked up manually](/api-reference/endpoint/get-transaction) (e.g. to obtain its status) using the `transactionId` field value.
<Note>
    Find out more about events on the [dedicated page](/events/events-overview).
</Note>
