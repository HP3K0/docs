Webhook notifcations are a crucial component to our payment flows, helping you stay informed in real-time whenever specific events occur on our platform. The main current usecase on PeoplesPay is tracking payment transactions, with more in the pipeline. Contact support to place requests for new event types and payloads.

## Event overview
The PeoplesPay platform will generate events internally in response to specific system states. These events will be sent to event destination, which are usually webhook endpoints, included in request payloads as a `callbackUrl` field.

### Delivery strategy
Events are delivered to the supplied `callbackUrl` when triggered on PeoplesPay. The event notification is sent as a `POST` request. The initial delivery is retried up to four times, using exponential backoff, if acknowledgement of receipt is not returned. We expect a 200 response, to mark an event as delivered. The first retry is triggered after 15 seconds, and every subsequent request is triggered after twice the delay.

## Event types
The PeoplesPay API delivers different types of events. Each has a different payload, but they will each include an `eventId`, which can be used to manage the event.

|Event type|Description|
|---|---|
|Transaction status update|This event type is created and delivered whenever a transaction status changes.|

## Event management
Events can be retrieved and delivery can be re-attempted, to effect particular changes in the client system via the webhook endpoint.

### Retrieving an event
Retrieve an event by calling the /get endpoint and passing the `eventId` as a URL parameter.

### Retrying event delivery
Retry event delivery by calling the /fire endpoint and passing the `eventId` as a URL parameter.
